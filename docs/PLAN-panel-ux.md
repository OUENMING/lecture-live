## 0.5 ⭐ 产品定位升级（2026-09-27，作者原话）

> 「产品定位已经**升级成了一个留学生的一个助手**吧，相当于上课的助手。他能听教授的总结上课所说的
> 东西、浏览课件、并且还能给学生进行复习，包括**记住学生上课没听懂的东西**，下课也能……（待确认）」

### 0.5.1 定位变了，但**筛选线不变**

⚠️ **从「字幕工具」升到「上课助手」，最危险的不是野心，是它让每一件事看起来都该做。**
过滤器仍然只有一条 —— 就是作者自己那条「**创新不能违反用户习惯、要回到产品本身的定位**」，
落成一句可执行的：

> **这件事有没有降低"每分钟的认知负荷"？**（README 的原始痛点：**跟不上语速**）

**过不了这条的，一律不进来** —— 不管它看起来多智能。

### 0.5.2 五项能力落进哪里 + 各自新增了什么

| 能力 | 落进哪 | 新增成本 |
|---|---|---|
| 听教授 + **总结** | §7 原子层 + 要点视图 | **原子层（最贵的一块）** |
| **浏览课件** | `~/.classlive/courses/<课号>/materials/` —— **已经在存了** | ⚠️ 只缺**「看」的入口**（现在只存不看） |
| **复习** | 课后笔记的复习层 —— **已有** | — |
| ⭐ **记住上课没听懂的东西** | **新的，而且是最值的一条** | 一个零成本动作（按一下 = 标记"这里没懂"），**与已有的 ⭐ 按钮同一形状**；课后自动变成复习项 |
| **下课也能看重点（笔记）** | 课后笔记的复习层 —— **已经存在** | ⚠️ 要定的**不是"做不做"，是"要不要在 app 里也能看"**（现在只存在于 Obsidian 里） |

⚠️ **更正一处我自己的表述**：我在对话里做梳理时，把「**AI 实时总结**」写成了"要点"、
排在第 3 位 —— **那是写小了。** 按 §0.5 的新定位，作者列的**第一项能力就是"听教授的总结"**
→ 它是**这套东西的头条**，不是边角。方案里它一直在（§7 总结面板 / §7.3 原子层 / §8 插入式总结），
但**优先级表述要按头条对待**。

### 0.5.3 ⭐ 「没听懂」这一条为什么是升级里最对的

- 它是产品定位那句「**跟不上语速**」的**直接解药**（不是又一个 AI 功能）
- 它是**用户主动给的信号**，**不靠 AI 猜** —— 正合 §2 原则 ①
- 它天然是**课后复习的锚**，而复习层**已经存在**
- **成本极低**：与 ⭐ 按钮**共用同一个交互**，不要求用户学新动作

### 0.5.4 贯穿的那根线：**一份「原子」，三个视图**

```
课前  卡片墙（frecency 排序）→ 有把握才倒计时
课中  字幕（主区） + 一块可收放的第二区（要点 / 已标的 ⭐ / 术语）
      插入：**只在讲者停顿处**插一行标记（常驻 · 不暂停 · 不推走正在读的）
      「这句重不重要」= **同一个判断** → 供 ⭐ 建议 与 要点骨架 两个消费者
课后  同一套原子跑完 → 笔记（已有）· 考试信息 brief.md（另一批）
```

→ ⭐ **这不是九个新功能，是同一份东西在三个时间点的三个渲染。**
正是仓库已有的那条原则 —— **一份配方，多个消费者**（`panel.py` 配方 / `objc_own` /
`paths.py` 全是这个形状）。

## 2. 设计原则（五条，每条都有出处；后面所有决定都从这五条推）

**① 不确定的判据不许靠近录音路径。**
出处不是新原则，是仓库既有的两条硬约束：`CLAUDE.md` 的「**不阻塞不变量**」（往流水线里加活先想它）与「**凡是要给别的脚本/进程看的判据，先问它出错时倒向哪边**」。
→ 直接推出 §0 决定 1：**不做音频内容自动识别课程**。它要「先转几句才知道是哪门课」，而出错时倒向的是**用错术语表**——整节课质量的延迟暴露错误。

**② 麦克风打开前必须有一个可见、可打断的过渡态。**
`[官方]` 橙点是**事后**才亮的（打开输入设备时通知 loginwindow），所以**系统帮不上忙，可见性必须由我们自己给**。
→ §3。

**③ 一条纪律只有一个定义点。**
仓库既有（`panel.py` 配方 / `objc_own` / `paths.py` / `courses.py` 全是这个形状）。
→ §5 的排序、§9 的重点判断、§7 的原子层，都必须是**单一来源 + 多消费者**。

**④ 引文必须能回源；不能回源的标注要降级。**
本轮我因为「逐字」标注不成立、以及转述了一个零引用的维基断言，各栽了一次。
→ 这份文档里每个数字后面都带口径标签；`[无明文]` 就写 `[无明文]`。

**⑤ 一切视觉数值服从 `docs/RESEARCH-macos-aesthetic.md`。**
同心圆角（**内 = 外 − 内边距**，不许硬编码）· 字号 13pt 默认 / 最小 10pt · **层级靠字重+字号+颜色三者** · 对比度 **≥4.5:1**（小字目标 7:1）· **不加字距** · 系统按钮**无 hover** · **整数坐标** · 强调色**节制**。

## 3. 启用逻辑

### 3.1 主流程

```
双击 .app
 └ macOS 按 Info.plist 起 Contents/MacOS/python → sitecustomize.py → execv(cl)
    └ cl 零参数分支 → entry_launch.py（**独立短进程**）→ 课程卡片面板
        │
        │  ⭐ 面板打开后立刻算排序（§5），然后判断「有没有把握」
        │
        ├─ 有把握 ──→ 最高分那张卡**置顶 + 高亮 + 显示倒计时环**
        │              「5 秒后开始 ECON10740　·　点别的卡就换」
        │                 ├ 不动 ──→ 倒计时结束 → 写 .course → 退出码 0 → cl 录课
        │                 ├ Esc / 关窗 / 点空白 ──→ 取消（退出码 1，**不录**）
        │                 └ 点别的卡 ──→ 换成那门课（**倒计时重置**）
        │
        └─ 没把握 ──→ 不倒计时，只出卡片墙（等用户点）
```

### 3.2 「有把握」的定义（必须是可断言的，不是感觉）

三个条件**同时**成立才算有把握：

1. §5 的 Layer 1 命中（今天这个时段确实是这门课）
2. 最高分**唯一**（没有并列）
3. 与第二名的分差 ≥ 阈值

⚠️ 阈值必须**从一个地方取**（§5 的常量），不能在 UI 里再写一遍。

### 3.3 倒计时：**5 秒，不是 3 秒**

| 依据 | 说了什么 |
|---|---|
| `[官方]` WCAG 2.2.2 的理由句 | 「**5 秒**够抓注意力，又不至于让人等不起」 |
| `[官方]` Gmail「撤销发送」 | 默认 **5 秒**（可选 5/10/20/30） |
| `[官方]` Apple 录屏 | **3 秒**（同类交互的 Apple 先例） |
| `[论文]` Netflix autoplay | ~5 秒，但 **62% 不喜欢** —— 原因见下 |
| ⚠️ `[官方]` WCAG 2.2.1 | 「几乎所有人都够」的基准是 **20 秒** |

→ 取 **5 秒**。**3 秒只够勉强看清是哪门课，不够"回顾自己的初衷"**（UChicago 实验里那句原话正是批 5 秒的）。
→ 不做 20 秒：那是「几乎所有人都够」的临床值，用在**每天一次**的动作上会让速度优势全没了。

### 3.4 ⚠️ 硬约束（这一节是本方案里**最不能省**的）

本轮最值钱的结论不是「用户讨厌倒计时」，是：

> **3–5 秒内没打断 → 录音已经在跑 → 用户不知道、或以为没开始。**

而**系统兜不了底**（橙点事后才亮）。所以：

1. **面板任何时刻都要有持久的「正在录音」状态**，且**一键可停**
2. ⭐ **「打断倒计时」与「停止录音」必须是同一个零成本动作**（`Esc`；以及单击卡片区域）
3. **录制中**面板不许自己消失——用户必须能随时看到它
4. 设置里**允许永久关闭自动开始**（正好满足 WCAG 2.2.1 的 Turn off 那条出路）
5. ⚠️ **不要把 `Return` 绑到「开始上课」**：`[官方]` HIG 给 Return 的收益是「视图能自动关闭」，而**面板不关闭，这个收益不存在**；误触的代价是**误开一节课**

### 3.5 退路（三层，都已经在了）

| 情形 | 行为 |
|---|---|
| `CL_NO_PANEL=1` | 跳过面板，照旧立刻录课 |
| 面板起不来（退出码 2） | 退回立刻录课 |
| 没课程可显示（退出码 3） | 退回立刻录课 |
| **用户主动关掉**（退出码 1） | **不录**（这是意图，不是故障） |

### 3.6 不做 / 待实

- ❌ **不做「修饰键点图标直通」**（作者提过）：双击由 **LaunchServices** 处理，修饰键在图标层面**未必传得到我们的进程**。原则上启动时读 `NSEvent.modifierFlags()` 能拿到，但**没实测** → 标为**待实**，不写进方案。
- ❌ **不做「双击直接进上次那门课」**：那是**无拦截点的静默启动**，违背原则 ②。

## 4. 信息架构：三种状态（不是一种布局的空数据版本）

`[惯例]` 全部无 Apple 明文；依据是 NN/g 的空状态三准则 + 真实产品做法。

### 4.1 空状态（0 门课，第一次打开）

`[无明文]` HIG 没有 empty state 页面；最相关的只有 `[官方]` Alerts 的「**Avoid showing an alert when your app starts**」。
`[惯例]` 反例被点名的是「**完全空着**」（既没说明也没入口，NN/g）。

→ **把「选择文件…」这个动作本身放大成整个面板的焦点**：一个居中的大号拖拽区 + 一句说清「拖课件进来，开始这门课」。
→ **这是两套布局，不是同一套的空数据版本。**
→ ⚠️ `[无明文]` 「整面板即 drop zone」**没有 Apple 先例**（最接近的是 Yoink：拖拽开始才从屏幕边缘出现）。

### 4.2 常态（几门课，同时在修）

就是现在的卡片墙 → §5、§6 打磨。

### 4.3 累积状态（修了几个学期之后）

⚠️ **先纠正一处**：`[无明文]`「按时间窗自动归档」在主流产品里**找不到先例**（Apple Photos 的 Recents **不是**时间窗）。
可直接抄的只有 **`[官方]` macOS「最近项目」那种「只截条数、不删数据」**。

→ **按学期分组、默认折叠上学期以前的**；**只把「最近这次上课在 30 天以内」的留常显**。
→ 阈值写成**一个常量**，且**不删任何数据**（只是收起）。
→ 这一步现在**不做**，但**布局上要预留分割点**（否则以后往定型布局里硬塞会更难）。

## 5. 排序：两层**字典序**（不是加法打分）

### 5.1 为什么是字典序

`[官方]` Mozilla 弃用旧分桶模型的四条理由里，第三条是「**系数太多，无法调优**」。
→ **不做加权求和**（那等于把 Mozilla 踩过的坑重踩一遍）。**先分档、档内再排。**

⚠️ **`[论文/论坛]` 明确的失败模式，必须绕开**：frecency 的 `总数 × 新旧` **乘积**形式会让**休眠项被重访一次就霸榜**（HN 48674366；`z`/`fasd` 同款 bug）。
→ **每次「开始上课」当一次独立冲量、各自衰减后求和**，不要 `总数 × 新旧`。

### 5.2 Layer 1（主排序 · 周期）—— 用桶，因为它**可断言**

数据来源：**声明为主**（每门课填「周三 14:00–16:00」），`[实测]` **历史兜底**（`sessions/` 文件名本来就带日期+时间）。

| 条件 | 档 |
|---|---|
| 今天有课，且 `now ∈ [start−30min, end]` | **A** |
| 今天有课，`now < start−30min` | B |
| 明天有课，且 `now ≥ 17:00` | C |
| 今天有课但已过 `end` | D |
| 其他 | E |

⚠️ **历史兜底只在置信够高时才参与 Layer 1**（否则退化成纯 Layer 2）：
`[实测]` 课表的**调课 / reading week / 期中停课看不见** → 会**自信地错**。
→ 判据：样本 ≥ 3 次、且该课号在一次以上的记录里落在同一时段。

### 5.3 Layer 2（同档内 · 历史）—— 冲量衰减

`f = Σ` 最近 **10** 次「开始上课」事件 `× 2^(−Δdays / 14)`

- **半衰期 14 天**（不是 Firefox 的 30 天）：`[实测]` 一个学期只有 12–13 周、多数课每周一次，30 天太长
- **只采样最近 10 次**：`[官方]` Firefox 同款做法（控制成本）
- ⚠️ **不要抄 zoxide**：它的 `1 周内 ÷2、否则 ÷4` 对**每周一次**的课几乎永远落在 ÷4 档，**等于丢掉全部新旧信息**
- 手动点击权重 1.0；倒计时自动开始 0.5（`[惯例]` 没有权威权重，这是我们的选择，**要写下来**）

### 5.4 冷启动

| 情形 | 行为 |
|---|---|
| 有课表声明 | **第一天就能排对** —— ⭐ 这是本场景比 Firefox 强的地方（课表是已知的） |
| 没声明、`sessions/` 也空 | 退化为 `last_session` 降序，再退化到课号字母序 |

### 5.5 失败模式与对策（**这一节比公式重要**）

| 失败模式 | 出处 | 对策 |
|---|---|---|
| 休眠课被误点一次就回顶 | `[论坛]` HN 48674366 | 冲量衰减（5.3），**不用乘积** |
| 每节课都开的课无差别霸榜 | `[官方]` Mozilla bug 710440（App Tabs） | 倒计时自动开始的冲量权重只给 **0.5** |
| 长假回来分数全趋零、头几次乱跳 | `[论坛]` HN 同篇 | 冷启动走 §5.4，不依赖历史 |
| 排序**无法评估**（用户不告诉你对错） | `[论坛]` 同篇 | **记一份「点了哪张卡」的日志**，否则永远回答不了「它准不准」 |
| 它把错的课排第一还很自信 | `[实测]` 调课/reading week 不可见 | §3.2 的「有把握」闸门 + **没把握就不倒计时** |

## 6. 卡片：视觉层级与四态

### 6.1 主按钮 vs 次按钮（**这条有 HIG 明文**）

`[官方]` HIG › Buttons 逐字：「use a button that has a **prominent visual style** for **the most likely action** in a view… so the system can apply an **accent color** to the button's background」

- **「开始上课」= 强调色填充的主按钮**
- **「选择文件…」= 纯描边/纯文字的次按钮**

⚠️ **别说成 HIG 规定了「填充+描边」这个配对** —— `[无明文]` HIG 没有这个具体配对；「一个 view 只能有一个 default button」出自 **AppKit 文档**，不是 HIG。

### 6.2 整张卡是一个大点击区（**有明文答案**）

`[官方]` HIG › Drag and drop（macOS 段）逐字：「Display a drag image as soon as people drag a selection about **three points**」

→ **位移约 3pt 才升级为拖拽，0 位移就是点击** —— 所以「卡片同时是点击目标和拖拽目标」**不冲突**，判据就是这 3pt。
⚠️ `[无明文]`「整卡是点击目标」本身没有 HIG 条文（`[惯例]` Web 侧常见）；HIG 只有 `Collections` 的「Use adequate padding…to keep focus or hover effects easy to see」与 Buttons 的「hit region of at least 44×44 pt」。

### 6.3 四个状态，**用两套不同的视觉手段**

| 状态 | 手段 |
|---|---|
| default | — |
| **拖拽悬停**（文件在这张卡上方） | **边框**亮起（+ `circle.slash` 当拒收时） |
| **prep 正在跑** | 卡内进度行（不是边框） |
| **今天大概率要用**（§5 命中） | **极轻的背景色**（不是边框） |

⚠️ **必须分两套**：拖拽反馈和「今天可能用这张」如果都用同一种强调，会互相抢注意力、分不清。

### 6.4 元信息：**星期几优先**

现在一行里挤了「7 份课件 · 73 条术语 · 上次上课 9/25」三种权重不同的信息。
`[论文]` Golding/Magliano/Baggett 1995：**2–14 天内的事件，人偏好用星期名**，更远才用日期。

→ **「上次上课：周三」**（超过约两周再补日期：「周三 9/17」）
→ **把「上次上课」从那一行里拎出来**，其余两项（课件数/术语数）降为更弱的次要文字。
→ ⚠️ `[无明文]` HIG 对这条没有任何规定；依据是认知科学，不是 Apple。

## 7. 总结面板

### 7.1 ⚠️ 照 Photoshop 抄**不可行**（三条硬约束，都已回源核实）

| # | 事实 | 出处 |
|---|---|---|
| 1 | **macOS 没有「窗口拼接」的系统 API。** `NSWindow.windowTiling` 这个符号**在 AppKit 文档里不存在**；15 的拖边缘 tiling 是**用户手势**，WWDC24《What's new in AppKit》**没有任何触发它的方法** | `[官方]` |
| 2 | 唯一白拿的是 `addChildWindow`，而且是**单向**的：「**moving childWin will not cause the window to move… but moving the window will cause childWin to move**」 | `[官方]` 逐字 |
| 3 | ⚠️ **「最小化」在这套窗上不通**：`miniaturize(_:)` 官方定义是「**displays the minimized window in the Dock**」，而本 app 是 `.accessory`（Dock 里没有图标）；且无边框窗必须 styleMask 含 `.miniaturizable` 才响应，而 `overlay.py` 的 style 是 `Borderless｜NonactivatingPanel｜Resizable`——**没有**；更麻烦的是 **styleMask 不能运行时补**（`overlay.py` 引 NSWindow.h:341） | `[官方]` + `[实测]` |

→ **Photoshop 那三态（拖动停靠 / 折叠成条 / 拖出变浮动）全要自绘**，还要在无边框非激活窗上额外处理 key window、miniaturizable、激活态三条坑。**成本 = 自己写一个小型 dock 容器。**

### 7.2 形状定案：**主窗内一块可收放的分栏，用「固定两态切换」而不是可拖分割**

**决定**：面板内让出一块区域，**一条按钮/轻标签在「全宽字幕 ↔ 62/38 两栏」之间切**。
左边字幕、右边要点列表，两边**各自独立滚动**。

⭐ **这不是「打不过约束才退让」—— 它本来就是更贴这个场景的交互。**
自由拖拽的分割线，对付的是「**用户每次想要的比例都不一样**」那种需求。
而我们这里：**只有两块内容，且合理比例基本不会因人而异**。
真正有用的操作是「**我现在只想看字幕**」或「**我现在想两个都看**」，
**不是「我想把总结区调到精确 43%」**。
→ **约束只是提前排除了一个本来就不该选的选项。**

`[惯例]` 佐证：主流产品里「显示/隐藏一个 pane」**全是二元开关** ——
Xcode 的 `Focus/Unfocus this Editor Pane`、VS Code 的 `Toggle Side Bar ⌘B` /
`Toggle Panel ⌘J`、Keynote 隐藏导航器、访达边栏。**没有一个把"调比例"当主要操作。**
`[官方]` HIG 也只说「**Consider letting people hide a pane**」+「**Provide multiple ways to
reveal hidden panes**… a toolbar button or a menu command — **including a keyboard shortcut**」
—— **它要求的是"能藏能露"，不是"能调比例"。**

**顺序**：**先做壳**（切两态），里面**先放已经存在的东西**（这节课已标的 ⭐ 重点 / 术语表），
**AI 要点后填**。→ 壳第一天就有用，而最难的那块（原子层，§7.3）可以单独成熟。

#### 7.2.1 为什么不做可拖分割（三条，都回源核过）

| # | 事实 |
|---|---|
| 1 | ⚠️ **掐断点不是"抓不到分割线"。** `[实测]`（本机 runtime 探针）：`NSSplitView` 自己 `acceptsFirstMouse` 返回 **True**、`mouseDownCanMoveWindow` 是 **False**、`.thin` **画 1pt 抓 5pt** —— **拖动本身完全成立**。真正掐断它的是**我们自己的三处**：① `panel.py` 的 `sendEvent_` 每次左键都 `activateIgnoringOtherApps_(True)`（与浮层"永不抢焦点"哲学冲突）② `overlay.py` 那条「非编辑态即 `_release_focus()`」会在分割线刚让面板成 key 的那一刻**把 key 抽走** —— 这是**时序竞态**，会做出**发抖/失灵**的拖拽 ③ ⚠️ **pane 用的裸 `NSView`/`NSVisualEffectView` 的 `mouseDownCanMoveWindow` 是 `True`** → **拖 pane 会变成拖窗口** |
| 2 | ⚠️ **鼠标穿透**：`ignoresMouseEvents` **只存在于 NSWindow**（子代理把整个 AppKit 头目录 grep 过，**NSView 没有** —— 网上写 `view.ignoresMouseEvents = true` 的是错的）→ **穿透开着，分割线必然全失效**，而且**没有"部分区域可交互"的官方 API**。⚠️ 仓库现状：穿透是**持久开关**，**唯一出口是菜单栏**（`overlay.py:581`：「开启后窗口忽略所有鼠标事件, 按钮会集体失效(单向死锁)」）→ 分割线会**加入那份"穿透下集体失效"的名单** |
| 3 | 另省三个坑：`autosaveName` 同名多实例互踩 / Auto Layout 下常不恢复 / 折叠态易丢；**裸 `NSSplitView` 没有折叠 API**（官方动画只在 `NSSplitViewController` 侧）；`splitView(_:constrainMinCoordinate:)` 官方 **Important** 明写「**If your split view uses Auto Layout to size its subviews, don't implement this method**」 |

⚠️ **诚实记录一条反向证据**：`[官方]` HIG › Split views **开门第一句**就把它定位成
「show **multiple levels of your app's hierarchy**… support **navigation between them**」（主从/层级）。
我们这两个 pane（**字幕 | 要点**）是**平级的两个流**，不是层级 ——
**就算做分栏，也是在用一个不在 HIG 描述范围内的用法。** 这条要留住，别装作有官方背书。

#### 7.2.2 将来若真要可拖分割 —— 抄这几条（都 `[官方]`/`[实测]`）

- ⚠️ **`isVertical` 是命名陷阱**：官方逐字「默认 **false**，表示水平分割线、视图**上下堆叠**」；
  要**左右并排必须显式设 `True`**（SDK 头最无歧义：*"whether the long axes of a split view's
  dividers are oriented **up-and-down (YES)** or **left-and-right (NO)**"*）
- **分割线不用加宽**：官方说 thin 会「propose an effective frame that's a little larger than the
  drawn frame, **to make it easier for the user to actually grab**」→ **实测 1pt 画 / 5pt 抓**
- `dividerThickness` 是 **readonly**，只能子类 override；⚠️ KVC `setValue(forKey:"dividerThickness")`
  **会抛 `NSUnknownKeyException`**（`setDividerThickness:` 不存在）——**偏方已死**
- **别补 `acceptsFirstMouse`** —— `NSSplitView` 自己 override 了并返回 True
- 用裸 `NSSplitView` 而不是 `NSSplitViewController`（后者逼你给每个 pane 造 `NSViewController`，
  且官方明说改某些属性**会抛异常**）
- ⚠️ **每一个 pane 都要显式 `mouseDownCanMoveWindow -> False`** —— 见 `CLAUDE.md` 雷区那条
  （这是同一个根因的**第三次**：默认值是 `!isOpaque`，所以磨砂面板上的新视图一出生就是 `True`）

### 7.3 ⭐ 分层：**原子层只增不改，视图可随时重算**

`[论文]` **链式更新有实测损失**：Chain-of-Key（arXiv 2407.15021）Table 1，Generate-Update 在
**纯文本**格式下 Gemini-Ultra 从首轮 **72.6 → 末轮 55.8 F1**（我逐格核过）。
⚠️ 精度限定：**同一模型的 JSON 格式只从 84.3 → 78.1**，掉得少得多 —— 所以这条损失的**量级取决于表示形式**，不是「链式更新必然崩」。我们的原子层是结构化的，正落在这条较轻的一侧。
`[官方]` DUC 2007 update task 的指令本身就写着「假设读者已读完前面**全部原文**，不只是你写的摘要」→ **从源重建**是事实标准。

```
转录（已有）
   ↓
原子提取（**只增不改**：这句带来了什么新信息 / 是不是重复）
   ↓                      ↘
课中实时视图（从原子算）        课后笔记（同一套原子跑完，已有 pipeline）
```

→ ⭐ **「同一套机制两个消费者」直接成立**（`[官方]` Teams 就是这个形状：同一份转录 → 会中 Copilot + 会后 Recap）。
→ **课中甚至可以不调模型**（只渲染原子）—— 于是「增量比全量省多少」这个**没有实测数字**的问题直接消失。

⚠️ **两条约束**：
- **必须节流**（按句数或按时间），且**不得与翻译抢**（`CLAUDE.md` 不阻塞不变量）
- 课后那条 pipeline **已经存在**（`obsidian_writer` 复习层 + `polish.py`）→ 真问题是**「原子」这一层要不要抽出来共用**，而不是要不要两套

### 7.4 俯瞰 + 下钻

`[惯例]` 真实产品：Teams Recap、Otter（摘要点时间戳回原文）、NotebookLM（每条结论回链原文段）。
`[论文]` 术语是 **attribution**（Rashkin et al., CL 2023）。

- **上面 5–8 条要点，每条可点开看它对应到转录里的哪一段**
- ⚠️⚠️ **下钻必须真对得上。** `[论文]` AAAI 2025 RCT：**有引用显著提升信任（连随机引用也提升）；但用户一旦去点引用、发现对不上，信任显著下降** —— 被查的随机引用跟没引用一样。且 `[论文]` RAG 里最高 **57% 的引用不忠实**。
  → **做不到真跳转的条目，就不给下钻入口。** 宁可没有那个 ▸。

`[惯例]` ⭐ 最佳先例是 **Zulip**：未读是一等公民、**光标落在最旧的未读而不是最新**、8.0 专门加了 Inbox 视图做「补看」。

## 8. 插入式总结（作者提的「插进滚动流 + 停 2–3 秒」）

### 8.1 证据判定：**一半成立，一半是一边倒的反对**

| 作者的主张 | 判定 |
|---|---|
| **AI 判断「该总结了」并自己决定时机** | ✅ **成立**。`[论文]` Rey et al. 2019 Table 3：系统切分 retention **0.42\*\*\*** vs 学习者自控 **0.19 (n.s.)**；且原文另有一条**正好说到本场景**：「先验知识**低**的学习者更应该用**系统定速**」（L2 + 新学科正落这一档） |
| **停 2–3 秒** | ❌ **差一个数量级。** `[论文]` Brysbaert 2019（190 研究/18,573 人）英文默读 **238 wpm** → **3 秒 ≈ 12 词**；`[论文]` Foroughi 2015：打断**专打理解**（**d=1.90**），且要 **15 秒**空白缓冲才把代价吸收掉；`[论文]` 停顿的收益来自**检索**（Ruhl 1987 是 2 分钟+同伴讨论；Szpunar 2013 是插入测验），**被动材料借不到这条** |
| **「读总结」有学习收益** | ⚠️ **不成立**（同上：收益在检索，不在停顿） |
| **用户往上翻 / 往下滑** | ✅ 但这是**已有的**规则（「上滚即停、回底恢复」），不应该由程序替他停 |

⚠️ **还有一条结构性事实**（不是研究）：**停住滚动 ≠ 停住讲座。** 音频继续走，读总结的那几秒是**永久丢失的讲座**。
⚠️ `[无明文]` 而且**没有任何产品故意停流 N 秒**：行业一致选「**停到你回来**」（Twitch 的 Mouseover 模式是唯一"过 5 秒自动恢复"的先例，但那是**悬停**触发的）。

### 8.2 改成什么形状

| 要素 | 决定 | 依据 |
|---|---|---|
| **何时插** | **只在讲者自己停顿处**（`vad.py` 的静音档 0.45–0.70s）—— 那里**没有新内容**，不欠账。且「讲完一个 point 停顿」正是「这段讲完了」的声学信号 | `[实测]` 现成机制 |
| **形态** | 插**一行标记**，不是整段：`📌 这里讲了 3 点 · 点开`（复用已有的 `⭐ Exam Focus` 那一行的形状） | 3 秒只够 12 词 |
| **暂停** | **不暂停。** 要读就用户自己滚（已有的「上滚即停、回底恢复」） | §8.1 |
| **消失** | **常驻滚动历史**，不自动消失 | 这样 2.2.1 的 time limit 与 1.4.13 的 Persistent **都不触发** |
| **展开** | 点击展开时**覆盖**不撑开 → 不位移 | 见下 |
| **位置** | **内嵌**（紧邻它总结的内容），**不是侧栏** | `[论文]` split-attention：互相指涉的信息分开呈现 → 外在负荷上升 |

⚠️ **内嵌 vs 侧栏是两股相反的证据，合起来指向同一个解**：
`[论文]` **split-attention** 说「分开呈现更差」→ 支持内嵌；
`[论文]` **transient information** 说「能回看时切分收益消失（0.40\*\*\* vs 0.14 n.s.）」→ 支持**可回看**。
→ **内嵌 + 常驻** 同时满足两边。⚠️ 但「内嵌 vs 侧栏」**没有直接对照实验**，这是**推理**不是定论。

⚠️ **绝不推走用户正在读的东西**：`[官方]` CSS scroll anchoring 的规范原文——DOM 在**可视区域上方**变化会导致「the page moving while the user is in the middle of consuming the content」。这正是 `overlay.py` 已经修过一次的 bug（「翻上去看整节历史不会被新内容拽下来」）。
→ **硬约束：只在用户处于底部、且在跟实时内容时，才允许插入。**

### 8.3 与标准的关系

`[官方]` WCAG 2.2.2（Level A）管**滚动内容**：自动开始 + 持续 >5 秒 + 与其他内容并行 → **必须给用户可控的暂停/停止/隐藏**；失败技术 **F16** 就是「滚动内容无暂停机制」。
关键术语 `paused` 逐字：**"stopped by user request and not resumed until requested by user"** → ⭐ **「到点自动恢复」按定义就不是 pause**。
⚠️ **但要说清**：WCAG 的 conformance 定义在 **web page** 上，**原生 macOS 浮层不直接受约束** —— 这是**原则**，不是**义务**。（会不会变成义务取决于采购/法条，那部分**未核**。）

## 9. 重点自动标注与校准

### 9.1 只用「明示」信号（与作者选择一致）

`[论文]` 明示用语在语言学里是 **relevance markers**（Zare 2019：60 场讲座 293 例、84% 前指式）。
⚠️ **但查到的所有研究都没把这些标记与考试内容对齐验证过** —— 它们只被研究话语功能。
⚠️⚠️ `[论文]` **语速放慢 / 停顿变长 / 音高：没有任何证据**。韵律凸显 = 焦点/新信息（Pierrehumbert & Hirschberg 1990），**跟"重要"不是同一概念**；重读词检测（Jurafsky）检测的是"重读"不是"重要"。

→ **第一批只用明示**，且它是**可机械核验**的（字符串在不在转录里）—— 与 `prep._verify` 同一形状。
→ ⚠️ **要与总结骨架用同一个判断**（原则 ③）：两处各自判断 = 一条纪律两处定义。

### 9.2 ⭐ 校准：三个必须改的地方

作者的想法（每门课/每个教授各自校准、不上模型、可审）**方向对**，但有三个统计学陷阱：

| # | 陷阱 | 改法 |
|---|---|---|
| 1 | ⚠️ **「放着不理」不能当负样本** —— 你可能没看见、在记笔记、或走神了。`[论文]` Joachims 2017 §1 逐字：「the naïve approach of treating a click/no-click as a positive/negative relevance judgment is **severely biased**」 | **沉默记成「未观测」**；只有**显式忽略**才算负（要加一个忽略动作） |
| 2 | ⚠️ **分母太小**：一个触发语一堂课只出现 2–3 次，67% vs 33% 全在噪声里。`[论文]` **Rule of three**：10 次全忽略只能说真实率 **< 26%** | 存 **(曝光, 确认, 忽略)** **三元组**；用 **Wilson** 区间不用裸比例；**n<20 只报计数不报率** |
| 3 | ⚠️ **冷启动 + 自锁**：`[官方]` SpamAssassin 的成例是**必须累积 200 ham + 200 spam 才启用**；且低分建议若不曝光就永远拿不到数据 → **自强化**（`[论文]` Jiang 2019 AIES "Degenerate Feedback Loops"） | 冷启动走**全局先验 + 收缩估计**；给低分建议**留少量随机曝光** |

### 9.3 好消息：⭐ 交互**已经存在**

`overlay.py` 已有「标记当前句为重点」按钮 → 写进会话文件的 `⭐ Exam Focus` → 课后笔记出「## ⭐ 我标记的重点」。
→ **只差「把建议也记下来」这一步，不需要新交互。**

## 11. 动效

`[官方]` HIG › Motion 的**原则**有，**时长与曲线一律没有**（原文对 macOS 是「No additional considerations」）。
⭐ `[官方]` 一条直接支持「高频微交互别加」：**「In apps, generally avoid adding motion to UI interactions that occur frequently」**。
可用区间（出自别处默认值，**不是 HIG 规定**）：`[二手整理]` macOS **0.20–0.35s**，超过 0.4s 几乎肯定太慢。

| 该有动效的三处 | 做法 |
|---|---|
| **排序重算导致卡片换位** | **匀速位移**（不是弹跳），让眼睛能跟着追踪。⚠️ 顺序变了却硬切，用户会一瞬间找不到熟悉的那张卡 |
| **进度** | 数字跳变配一条**很轻的进度条填充** |
| **结果出现** | 短暂**淡入**，不要和进度同时硬切内容 |

- **其余（卡片 hover、按钮按下）零动效**（HIG 明文 + 美学宪法的「不加油腻的微交互」）
- ⚠️ `[官方]` WCAG 2.3.3 与「间接交互触发的动效」：**跟随 macOS Reduce Motion**，插入类动效**只 fade 不位移**

## 15. 调研总账（2026-09-27 · 第二轮，共四路）

> 起因：一份外部审计报告（第二版）提了一批建议。**逐条回源核过、并按我们代码的实际形态重新定级。**

### 15.1 报告里**被证据推翻**的三条

| 报告的主张 | 实际 | 出处 |
|---|---|---|
| 「1 行草稿是明确的不合格设计」 | ⚠️ **不准确。** 行业规范里 **1 行是首选常态**（Netflix 逐字：「**Text should usually be kept to one line**, unless it exceeds the character limitation」），**2 行是上限**。→ 真正不合格的是「**1 行 + 溢出裁剪**」—— 没有任何规范允许裁掉长句 | `[官方]` Netflix Timed Text Style Guide §4；BBC §3.8/3.9 |
| 「用 LocalAgreement 做**冻结前缀变灰**」 | ⚠️ **没有先例，而且极性是反的。** 所有主流实时字幕（Zoom/Teams/Meet/YouTube/Apple）**都不做已确认/未确认的视觉区分**；Berke 的 128 人 DHH 研究里**显示置信度被评为「分散注意力」**；`[论文]` CHI 2023《Modeling and Improving Text Stability in Live Captions》(N=123) 的**整个立论是把 interim 改写当缺陷去消除**。唯一正面先例极性相反：Piquard-Kipffer 2015（10 名聋人）**10/10 偏好「高亮已确认正确的词」** | `[论文]`+`[官方]` |
| 「加课程资料最高优先（含建检索）」 | ⚠️ **方向对，但做法反了。** `[论文/厂商]` 小语料能塞进单次 ~150–200k prompt 时**应直接跳过切分与向量库**；⚠️ 而长上下文**不是免费的**（Chroma《Context Rot》测 18 个模型：越长越差；《Lost in the Middle》） | `[论文]` |

### 15.2 报告里**成立且值得做**的

### 15.3 ⭐⭐ 三条**改变设计**的新证据

**① 「按下去那一秒，学生也不知道自己不懂什么」**
- `[论文]` Chen & Kizilcec 2020（LAK，**29,511 名学生 / 中国 12 所大学**）：「我不懂」按钮**漏掉大量真实困惑**；学生用「**收藏**」比用「我不懂」多 **10 倍**
- ⭐ `[论文]` Thiede et al. 2003：**延迟**判断把元认知 gamma 从 **.37 抬到 .70**；**当场判断 gamma = .10（≈0）**
- → **❓ 记的必须是「时间范围」而不是「一个句子」**（作者已选「回退十几秒」，**正好落在这条证据上**）
- → ⭐ **⭐ 与 ❓ 应是同一个手势、两个 tag**，不是两个并列按钮（否则「我不懂」那条 10× 的差距会重演）

**② `[论文]` Dunlosky et al. 2013 把「summarization（总结）」评为低效用**
（高效用只有 practice testing 与 distributed practice）
- → ⚠️ **这对"AI 替你总结"是直接不利的**
- → 第二区的价值主张**必须从「总结」挪到「导航 + 你自己的信号」**（Context Rail 的方向因此被证据支持）

**③ ⭐ 草稿显示模式有权威答案** —— 完整台账 + 全部一手引用见 `docs/RESEARCH-live-caption-rollup.md`
- ⚠️ **本行原写「§79.103」是我自己写错的（2026-09-27 自纠）**：§79.103 是**解码器硬件**条款
  （eCFR 标题逐字 `Closed caption decoder and display requirements for apparatus`），**通篇无三模式字样**。
  真正的一手是 **47 CFR §15.119**，逐字：`Roll-up style captioning is initiated by receipt of one of
  three Miscellaneous Control Codes that determine the maximum number of rows displayed simultaneously,
  either 2, 3 or 4 contiguous rows.`
  同一节还定死三条我们要照做的：**base row 固定在底、只有它接收新字** ·
  **顶出的行 `erased from memory and from the display`（无回滚缓冲）** ·
  **上滚 `must appear smooth… no more than 0.433 second`**
- ⚠️ **§15.119 的 roll-up 正文只存在于 2009 版**（我拉了 2025 版，grep 不到）→ **已非现行条款**；
  接替的 ANSI/CTA-608-E 在付费墙后 → `[未核]`
- `[官方]` ⭐ BBC **§21.5** 逐字：「**Two-lines of scrolling text should be used.**」
  ＋「Live subtitles should appear **word by word, from left to right**」
  ＋「`ebutts:multiRowAlign` should be avoided … since it can result in lines being moved horizontally
  whenever a new word appears」
- `[官方]` BBC **§3.3**：「a maximum subtitle length of **two lines** is recommended」（16:9/4:3/1:1）
- `[官方]` W3C 逐字：「**Roll-up captions are typically used for live captioned content**」
- `[官方]` FCC 14-12 ¶39：「Usually **two to three lines** of text appear at one time」
- 🆕 `[实测]` 我们的草稿窗口：**1 行只装得下约一半**（🔢 数字归台账 `docs/RESEARCH-live-caption-rollup.md` §4，别在这儿再抄一份）
- → **我们的草稿要改成「2 行 roll-up」，不是「word-wrap」** —— 后者会把长句挤成多行再裁掉

### 16.2 探针规格（**不改产品，只出数字**）

- **脚本**：`docs/experiments/probe_atomic_summary.py`
- **输入**：仓库里**已有的真实 sessions 文件**（不新录、不碰真实数据）
- **做法**：模拟流式，每 5 分钟切一段 → 调原子提取 → 打印要点
- **产出**：`/tmp/summary_eval.json`（要点 ↔ 原文行号）
