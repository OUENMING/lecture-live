# 计划：段落侧栏（字幕条之外，按段整合、整段重译、可展开收起）

> **状态**：只有计划，没写代码（2026-10-14 作者：「侧边栏这个放入计划先」）。
> **动手前读**：本文件 + `note_merge.py` 文件头（整句重译的实测与坑）+ `live_summary.py` 文件头（章节窗口）。
> ⚠️ 本文不抄行号，只写符号名。

## 一、要解决什么

字幕条是**逐句**的：一句话被 12 s 切段劈成两三行、各自翻译，读起来是断的。课后笔记已经治了
（`note_merge`，3 节真课盲评通顺 2.9 → 4.6），但**课上**看不到。作者想要的是 LecSync 那种：
讲完一段，把这一段的内容整合成通顺的一块，放在旁边一栏，可展开收起。

## 二、调研结论（2026-10-14，来源等级见括号）

| 结论 | 依据 |
|---|---|
| 「字幕条 + 独立转写面板」两层结构是现成惯例 | Teams 字幕/转写分离（Microsoft 365 路线图 RM495454，2025）；Zoom 字幕 + 侧栏转写（Lehigh 文档）|
| **没有**厂商公开说过「已显示内容整段重译」 | LecSync / Otter / Teams / 飞书妙记 / Wordly / KUDO 都没查到 —— 这是我们的差异点，**要自己 A/B** |
| 已显示文字被反复改写是最伤阅读的 | Arivazhagan et al. IWSLT 2020（arXiv 2004.03643）；Google 2021-01 稳定化博客（mask-k）|
| 只靠停顿切段会过切（日语讲座：召回 85%、精度 20%）| Kitade 2004 Interspeech；停顿 + 话语标记更稳：Kawahara IEEE TSAP 2004 |
| ASR 厂商的「段落」都是**事后**的（标点 / 停顿启发式）| Deepgram paragraphs、AssemblyAI FAQ —— 实时成段得自己做 |
| 自动滚动：用户上滚即暂停，回底恢复，给「回到最新」 | 只有用户诉求类来源（低置信），但与本仓 `RESEARCH-live-caption-rollup.md`「上滚即冻结」一致 |

⚠️ 上表来自一个子代理的调研，**引用前回源核对**（本仓纪律）。

## 三、本仓实测（6 节真课，`sessions/` 只读）

按「上一行有句末标点 + 时间戳间隔 ≥ G 秒」切段：

| G | 每节段数 | 每段时长 p50 | 每段行数 p50 |
|---|---|---|---|
| 6 s | 118–158 | 12–14 s | 2–4 |
| 10 s | 78–125 | 13–25 s | 3–7 |

⚠️ 时间戳是**发出时刻**不是停顿，噪声大；正式做要用 VAD 的段间静音（`vad.Segmenter` 有）。
→ 停顿切出来的是**段落**（十几到二十几秒），太碎当不了**话题**；话题要用现成的章节（`live_summary` / `chapter.py`）。

## 四、方案：两层

```
┌ 字幕条（现状，不动）┐   ┌ 段落侧栏 ─────────────────────── [收起] ┐
│ 逐句草稿 → 定稿      │   │ ▾ 需求曲线为什么向下倾斜        （章节） │
│                      │   │   价格上升时，消费者会少买……（整段重译） │
│                      │   │   但如果是吉芬商品……                     │
│                      │   │ ▸ 弹性的定义                    （收起的）│
│                      │   │   ……正在听（这一段还没封口，不出字）     │
└──────────────────────┘   └──────────────────────────────────────────┘
```

1. **段落 = 一次封口、一次成稿、之后不改。** 封口条件：上一句有句末标点 **且** VAD 段间静音 ≥ 阈值
   （起点 1.5 s，要在真课上扫），或段长到 90 s 硬封。封口后把这一段的定稿 EN 按 `note_merge.runs`
   并句、**整段一个请求**重译成中文段落（不是逐句；一段 3–7 句，比 note_merge 的单句大，要先验证
   「批量对错号」那个坑在段落粒度上还在不在 —— note_merge 文件头记着 12 句一批时 37/150 句对错了号）。
2. **话题分组 = 现成章节。** `live_summary` 的章节一出来，就把它覆盖的段落归到这个标题下；
   旧章节默认收起（▸），当前章节展开（▾）。章节还没出来的段落挂在「当前」下面。
3. **放哪**（⚠️ 待作者拍板）：
   - A. 替代现有「纲要」视图（`overlay` 的 `_tv_mode == "outline"`），原位切换 —— 改动小；
   - B. 悬浮窗旁边单独一个面板 —— 更像 LecSync，要动 AppKit 布局（`panel.py` 配方 + 新窗口）。
4. **滚动**：沿用 `transcript_view` 的「上滚即冻结、贴底才跟」；冻结时给「回到最新」。

## 五、成本与延迟（估算，要实测）

- 请求数：每节 ~80–150 段 → 同数量的 DeepSeek 请求，每次 ~300–600 token 入、~200 出。
- 段落出现在封口后 ~2–4 s（等静音 + 一次 LLM）—— 侧栏本来就不追实时，字幕条管实时。

## 六、步骤与判据

1. **离线先做**：拿 3 节真课的 `sessions/` 跑「切段 + 整段重译」，盲评对照逐句拼接（同 `docs/experiments/fragment_merge_20261014/` 的方法），
   且**专门查对错号**（段内每句的中文能不能对回自己的 EN）。不过关就退回「段内逐句重译、再拼」。
2. 扫封口阈值：段数 / 段长分布 + 人工看 20 个边界切得对不对。
3. 选 A 或 B，做界面；**拍图给作者看过再推**。
4. 开关 `CLASSLIVE_PARAGRAPH_PANEL`（登记 HANDBOOK §6.1）。

## 七、一并评估过、**不做**的两条（2026-10-14）

| 提议 | 结论 | 依据 |
|---|---|---|
| Worker 拿到 Groq 英文后直接在云端调 LLM，把原文+译文一起推回（省一次往返）| ❌ 不值 | 实测 Mac ↔ `asr.bldcam.page` 整个往返 31–55 ms（复用连接更少）；首字中文 ≈3 s 的大头是闸门 2.5 s（`classlive-draft-layer-decision`）。省 ≤50 ms，却要把翻译的上下文窗口 / 术语表 / 前缀缓存 / 流式打字全搬进 Worker，DeepSeek key 也要上服务器 |
| 短句（<10 词）直接沿用草稿译文，跳过定稿重译 | ⏸ 先量再说 | 3.9.4 起草稿译文已按句锁定、先上屏；定稿那次请求同时做 **EN 矫正**，跳过就丢矫正。值不值取决于「短句定稿 EN 与最后一版草稿 EN 一字不差」的比例 —— 测试报告里有两样数据，先量这个比例 |
