## 1. ⭐ 核心洞察：三件事其实是**同一个功能**的三个面

（这一条来自外部评审 2026-09-26 的建议，我核对后**认同并做了细化**）

| 面 | 表面上看 | 实际上是 |
|---|---|---|
| **入口** | 「一个上传文件的界面」 | **开课前的准备动作** —— 不是通用上传框 |
| **课件** | 「用户要放 PPT 进来」 | **候选术语的词源** |
| **Obsidian 可选** | 「换个地方存」 | **换一个渲染目标** |

### 1.1 入口 = 开课前的准备，不是通用上传框

某门课**第一次用之前**，把这门课的 syllabus / 课件拖进来 → 批量抽词 →
生成**这门课的候选术语表**。

触发时机从「上课时听到生词手动补」变成「**开课前一次性导入**」。
（运行时那条路已经有了：`build_notes.TermNotes` + `term_notes_auto.json`
—— 实测 `build_notes.py:488`，缓存文件 13 KB。）

**而且课件通常是真实的 PDF / PPTX（不是照片）**，文本抽取比"上课实时截屏 OCR"
简单可靠得多。

### 1.2 ⭐ 一次提取，两个出口（这是我对评审建议的细化）

评审说「`build_notes.TermNotes` 直接就有了更高质量的种子数据」——
方向对，但**要分清两个不同的产物**，它们吃的是同一份候选词：

```
  课件 PDF/PPTX
        ↓ PDFKit + stdlib zipfile 抽文本（零新增依赖）
          ⚠️ **不是 Docling** —— 见 PLAN-notes-and-ui.md §7.3 的作废横幅
        ↓ LLM 抽候选词（**新写的 prompt**）
          ⚠️ **`SYS_CLASSIFY` 抽不出词** —— 它的输入是「已存在的术语列表」，职责是分档。
             判据照抄它（中英对照价值），但抽取本身要新写。2026-09-26 回源码核实。
   候选词列表
        ├──→ glossary/<课号>.txt      ← 注入翻译 prompt（一行一个英文词）
        └──→ term_notes.json          ← 屏幕上的通俗解释（已有流水线）
```

**一份提取，两个出口。不需要新建任何数据管线。**

⚠️ **但有一条不能忘**：`glossary/<课号>.txt` 里有**两类词**，只有一类课件能给：

| 类别 | 例子 | 课件能给吗 |
|---|---|---|
| 领域术语 | `joule` / `OLS` / `regression` | ✅ 能 |
| **课号 + 教务词** | `ECON10101` / `Brightspace` / `deadline` | ❌ **不能** |

`glossary.example.txt` 里明写着：「**课号必须全列在这里** —— 同一院系的课号往往
发音极近，不给模型候选，它必然听混」。
→ **自动生成只能追加，绝不能覆盖**；课号那一段永远手写。

### 1.3 Obsidian 可选 = 多一个渲染目标

评审这条说得对，**但它有一个前提还没满足**：

> 「如果 `obsidian_writer.py` 已经拆成『生成结构化数据』+『渲染成某种格式』两段，
> 那么『没有 Obsidian 就存文件夹 + PDF』就只是多加一个渲染目标」

**⚠️ 它还没拆。** `_render_note()`（`obsidian_writer.py:497`）是**一根到底的字符串拼接**，
内容和 Obsidian 语法（callout / emoji / `<sub>`）焊死在一起。

**所以「多一个渲染目标」这句话省掉了那一步重活 —— 拆本身才是工作量。**
拆法见 §3 的接缝 ③。

### 2.4 这两条的调研与评估（2026-09-28，按 `research-sop`）

> 调研范围：① 开源界「本地个人知识 + 全文检索 + AI 问答」的**现成项目与架构**
> ② 说话人识别（闭集辨认 + 拒识）的**开源方案、成本、以及有没有更省事的路**。
> 按 `research-sop`：源 ≥2 独立、分信任层、引用逐条回源、结论标置信度。

#### A. 全局检索 + 并入 AI

**架构对比**（`[项目·已核]` = 读了仓库 README/架构文档）：

| 项目 | 检索层 | 上下文组装 | 要向量库吗 |
|---|---|---|---|
| **screenpipe** | **SQLite + FTS5，零向量索引** | 模型发 query → SQL → JSON | **不要** |
| **khoj** | 本地 bi-encoder + cross-encoder 重排 | 重排后取前 N | 自存嵌入 |
| **reor** | LanceDB（嵌入式） | chunk + embed → RAG | 要 |
| `[官方]` Anthropic contextual retrieval | Contextual Embeddings **+ Contextual BM25** | 每块 50–100 token 定位说明 | 要 |

**三个数**：
- 混合检索确实赢，但边际递减 —— Anthropic 实测 top-20 失败率：纯嵌入 **5.7%** →
  **+BM25 2.9%** → **+重排 1.9%**。**BM25 的边际（−14 点）不如重排（−18 点）。**
- `[论文]`《Lost in the Middle》逐字「performance is often highest when relevant
  information occurs at the **beginning or end**」，且「**even for explicitly
  long-context models**」。⚠️ 它**没给**"多少 token 开始退化"的阈值，别编一个。
- ⚠️⚠️ **我在本机实测的**：SQLite 3.43.2 有 FTS5，但**默认分词器对中文直接失效** ——
  ```
  搜 '垄断' -> 0   搜 '边际成本' -> 0   搜 '定价' -> 0
  搜 'monopoly' -> 1     ← 英文正常
  ```
  （与调研查到的 issue「porter unicode61 tokenizer cannot match CJK」一致。）
  → 中文语料上 **FTS5 不是开箱可用**：要么 trigram（接受 <3 字的坑），要么**别用 SQLite 索引**。

**评估**：
- ⭐ **先做「元数据 + 关键词」层，不要从向量库起步。** 最接近的同类 screenpipe
  （24/7 本地采集 + 搜索 + AI）**只上 FTS5**。
- ⭐ **本项目的语料结构化程度反常地高** —— 每份文件都带**课号 + 日期 + 标题层级**
  （`sessions/<日期>_<时间>_<课号>.md`、`Lectures/` 的 `##` 分组）。
  向量检索**看不见这些**，而它们恰好回答「最近讲了什么」这类问题
  （**元数据过滤 + 按时间排序，几乎不需要语义**）。
- **语义层等有实测需求再加**，加的时候照 Anthropic 那套（块 + 定位说明 + BM25 + 重排），
  **不要只上纯向量**。
- ⚠️ 与 §6「向量库 / 检索」的关系见 §2.3 末尾。

#### B. 教授声音识别 → 自动载入术语表

⭐⭐ **最大发现：`sherpa-onnx` 自己就带声纹识别 —— 而本项目已经在用它跑 ASR。零新依赖。**
**本机核实过**（`sherpa_onnx 1.13.8`，`ClassLive.app` 里那个 python）：

```
✅ SpeakerEmbeddingExtractor · SpeakerEmbeddingExtractorConfig · SpeakerEmbeddingManager
   SpeakerEmbeddingManager 的方法：add · all_speakers · dim · num_speakers · remove · score · search · verify
```

`search(emb, threshold=…)` **低于阈值返回空串** —— 「闭集辨认 + 拒识」是它的**原生语义**，
不用自己写阈值逻辑。模型 `3dspeaker_..._campplus_sv_en_voxceleb_16k.onnx`
**29.6 MB**、上游 3D-Speaker 是 **Apache-2.0**、CPU、`provider="cpu"`。
⚠️ sherpa-onnx release 页逐字写着「Each model has its own license」—— **许可逐个核**，不是统一的。

**时长够不够**：`[论文]` NIST SRE16 —— **≥40 秒差异很小**，但 30→20→10 秒**急剧下降**；
MIT LL 语料规范要求每段 **≥30 秒**。→ **「上课前几分钟」远超够用**。
⚠️ 真正的退化源是**信道不匹配**（注册用的麦克风 ≠ 教室的麦克风）—— 要不要去教室录注册样本，是个现实问题。

**「有没有更省事的路（用转录文本认课）」—— 两路独立实测都否了**：

| 谁量的 | 窗口 | 认得出 |
|---|---|---|
| 我（本机真实 `sessions/`，18 节真课） | 前 6 分钟 | **1/18** |
| 我 | 前 15 分钟 | **2/18** |
| 调研代理（独立跑） | 前 15 分钟 | 4/16 = 25% |

课号字面 **0/18**、课名独有词 **0/18** —— **教授不报课号也不说课名**，课上讲的是内容不是元信息。

**现成项目**：⭐ **没找到任何「靠教授声音自动认课」的项目**，最接近的是人脸考勤与自动录课。

**评估**：
⚠️ 它的失败模式**正是 §2.3 刚要避开的那一个**：认错课 → 载入错术语表 →
那门课**每一句翻译都在用错词**，且要到课上才发现。而它省下的只是**面板里的一次点击**。

→ **值得做，但做成「建议 + 一次确认」，不自动切换** —— 与批量归档（`PLAN-entry-panel.md §7.10`）
**完全同构**：同一个形状（系统猜 → 摆给人看 → 点头才写）、同一条理由（错了不可撤）。

#### ⚠️ 作者 2026-09-28 的追加设想：「弹窗确认 → 双击直接开课」

> 原话：「可以做一个弹窗或者提示，然后点确认时候就载入数据表，那这样子的话其实就可以
> **双击直接开课**了，是不是这样子？」

**逐条核过代码：技术上成立，但我不建议。三个代价，第三条最要命。**

**① 前几分钟**没有**术语表 —— 而那几分钟正是最需要它的时候。**
声纹要 **≥30 秒**才准（NIST SRE16：40 秒以上差异很小，但 30→20→10 秒**急剧下降**）。
也就是说开头这几分钟的译文是在**没有课程术语**的情况下出的。
而术语表是**每句全量注入**的（`translator.course_term_list` 的 docstring 逐字
「这些词每句全量注入」），它正是翻译质量的主要杠杆之一。

**② 现在课号是「启动时读一次」，换课要新加机制。**
```
cl:51        COURSE="$(cat .course)"                     ← 启动时读一次
cl:225       COURSE="$(cat .course)"                     ← 面板退出后再读一次
main.py:826  load_translator(..., course=args.course)    ← 只此一次，那时还没开录
main.py:832  load_cloud_translator(..., course=args.course)
```
「跑起来之后再换课」要动：`.course` 重写 · translator 换术语表 · `writer` 换课号 ·
落盘跟着换。而仓库里还压着一条**「课号不许中途变」**的隐含假设
（`_parse` 认会话抬头、`paths.course_dir` 的容错解析）。

**③ ⭐ 它一步都没省 —— 这是最讽刺的。**
| | 现在 | 这个设想 |
|---|---|---|
| 步骤 | 双击 → 看 5 张卡 → 点 1 张 | 双击 → 开录 → **等几分钟** → 弹窗 → 点确认 |
| 点击次数 | **1** | **1** |
| 等待 | 0 | **几分钟** |
| 开头几分钟的术语表 | ✅ 有 | ❌ 没有 |

**除非那一下确认是自动的** —— 而那正是作者 4 小时前刚否掉的失败模式（认错课 → 术语表污染）。

#### ⭐ 想省那"看一眼"：有个便宜得多的做法

2. **⚠️ 没人给出规模分界线。** HN 那个 **722 分 / 360 评论**的帖子（「RAG died to better AIs…
   nothing but a **grep tool over a pile of text files**」）**全帖没有一个人给出
   "多少文档 / 多少 token 就该上索引"的数字**；多篇都明说没有。**别编一个。**
3. ⭐ **繁中那篇的结论比数字更值钱**（12k 篇规模）：Hit@1 **39.4% → 63.6%**，

#### ⭐⭐ 中文那关：**我在本机验了修法，7 行、零依赖**

`[实测]` FTS5 默认 `unicode61` 把整段 CJK 当**一个 token**，且 `MATCH` 查的是
**token 相等而非子串** → §2.4 A 里量到 `垄断` → 0 命中。修法：

```
入库：把中文切成 bigram、英文按词切，空白连接      ← ingest 与 query **同一份变换**
  这节 节课 课讲 讲了 了边 边际 际成 成本 本和 和垄 垄断 断定 定价 monopoly pricing

搜 '垄断' -> 1   搜 '边际成本' -> 1   搜 '定价' -> 1
搜 '垄断定价' -> 1   搜 '成本' -> 1   搜 'pricing' -> 1     ← 全部命中
```

⚠️ 内建 `trigram` 不是替代品：**它不做任何分词**（`sqlite-better-trigram` 的 README 逐字：
`i am a bird` 查 `MATCH 'a bird'` 返回空）。⚠️ Meilisearch 的 Rust jieba 端口
**用简体词典且换不掉**（那位繁中作者离开它的原因）—— 别踩。

#### 重点自动标注（`PLAN-panel-ux.md §9`）—— 现有材料的摘要

**它已经避开了三个坑**（都有出处，不是我的偏好）：

1. **只用「明示」信号** —— `[论文]` 语速放慢 / 停顿变长 / 音高：**没有任何证据**。
   韵律凸显 = 焦点/新信息（Pierrehumbert & Hirschberg 1990），**跟"重要"不是同一概念**。
   明示用语（`this will be on the test`）则有 `[论文]` Zare 2019（60 场讲座 293 例）。
   ⚠️ 但**所有研究都没把这些标记与考试内容对齐验证过**。
2. **校准的三个统计学陷阱**：① 「放着不理」不能当负样本（`[论文]` Joachims 2017 逐字
   「treating a click/no-click as a positive/negative relevance judgment is **severely biased**」）
   ② 分母太小（`[论文]` **Rule of three**：10 次全忽略只能说真实率 < 26%）→ 存
   **(曝光, 确认, 忽略)** 三元组，用 **Wilson** 区间，**n<20 只报计数不报率**
   ③ 冷启动自锁（`[官方]` SpamAssassin 成例：**累积 200 ham + 200 spam 才启用**）
3. ⭐ **交互已经存在** —— `overlay.py:766` 的 ⭐ 按钮已写进会话文件的 `⭐ Exam Focus`，
   课后笔记已出「## ⭐ 我标记的重点」。**只差「把建议也记下来」这一步，不需要新交互。**

## 4. PDF 引擎选型（**已修正，我上一版结论有错**）

### 4.1 ⚠️ 先纠正我自己

上一轮我说「WeasyPrint emoji 变豆腐块」—— **那是错的**。
真实原因是**我的 CSS 只写了 `Noto Sans SC`，没写 emoji 字体栈**。
加上 `'Apple Color Emoji', 'Apple Symbols'` 之后重测：

| | 修正前 CSS | **修正后 CSS** |
|---|---|---|
| `CIDFontType0` 命中 | 1 | **0** |
| `LastResort` 字体数 | 2 | **0** |
| 渲染结果 | 🎯 变空方框 | ✅ **彩色 emoji** |

**问题在我的 CSS，不在 WeasyPrint。**

（顺带：我第一次的自检脚本还有个 bug —— 正则的字符类漏了 `.`，
而字体名是 `COQGKQ+.LastResort`，导致误报"命中 0"。已修。）

### 4.2 两条路的实测对比

| | **WeasyPrint** | **WebKit**（`WKWebView.createPDF`） |
|---|---|---|
| 中文 | ✅ | ✅ |
| emoji | ✅ 彩色 | ✅ 彩色 |
| 字体回落 | 0 | 0 |
| 速度 | 跑 **515 行真实笔记**：**5.5 s** | **0.7 s** —— ⚠️ 但那是 **31,941 B 的小测试文档**，**没在真实笔记上跑过**（附录见 `RESEARCH-entry-and-export.md` §3.2） |
| 要装什么 | `uv pip install weasyprint` **+ `brew install python pango libffi`** | `uv pip install pyobjc-framework-WebKit` |
| 跨平台 | ✅ 是 | ❌ 仅 macOS |
| 渲染引擎 | CSS 子集（行为可预测） | 完整 WebKit |

### 4.3 评审的建议与事实的出入

评审说：「给普通用户用，**前者（WeasyPrint）更省心**」，理由是**跨平台、
不依赖系统组件**。逐条核对：

- ❌ **「不依赖系统组件」在 macOS 上是反的。** WeasyPrint 官方文档逐字：
  > "The easiest way to install WeasyPrint on macOS is to use Homebrew.
  > When Homebrew is installed, install Python, Pango and libffi: `brew install python pango libffi`"
  （[doc.courtbouillon.org](https://doc.courtbouillon.org/weasyprint/stable/first_steps.html)）
  装不上会报 `cannot load library 'libgobject-2.0-0'`。
  而 WebKit 是**系统自带框架**，PyObjC 绑定是纯 Python 包装 —— 谁更"依赖系统组件"是反过来的。
- ❌ **「跨平台」对本项目价值为零。** README 写明只支持
  **macOS + Apple Silicon**（本地推理依赖 MLX/Metal，悬浮窗依赖 AppKit）。
- ✅ **评审没提但成立的**：WeasyPrint 的渲染是**确定性的、版本可 pin**；
  WebKit 跟随系统版本，macOS 升级可能改变输出。

### 4.4 结论

**选 WebKit。** 但理由不是"WeasyPrint 不行"（它行），而是
**「朋友要装什么」**：朋友按现在的 README 装，**全程不需要 Homebrew**；
引入 WeasyPrint 会把 Homebrew 变成新依赖。

⚠️ 而且这个决定**可逆**（§3 接缝 ③）—— 真被 WebKit 咬了，换成 WeasyPrint 只是换一个后端。

## 5. P1 的三个坑（都已实测）

### 5.1 ⚠️ 没有单实例保护 —— 双击会起两个

全仓搜 `single.instance|flock|pidfile|已在运行` → **0 命中**（唯一的锁是 `update.py`
自己的 `update.lock`，只管更新器）。

双击两下 = 两个 `main.py`、两个 `InputStream` 争同一个麦克风、
**两个悬浮窗叠在一起**、两倍 API 花费。
（会话文件名带 `%H%M%S`，所以**文件不会互相覆盖** —— 那层是安全的。）

**这是"改成双击"新引入的风险。**

### 5.2 PATH：Finder 启动时只剩 `/usr/bin:/bin:/usr/sbin:/sbin`

实测逐个查过 `cl` 用到的所有命令，**只有两个会找不到**：

| 命令 | 实际位置 | 影响哪条路径 |
|---|---|---|
| `uv` | `~/.local/bin/uv` | 只有 `cl update` 的**补依赖**分支 |
| `ffmpeg` | `/opt/homebrew/bin/ffmpeg` | 只有 `cl file` |

其余（`git`/`shasum`/`find`/`grep`/`sed`/`tail`/`head`/`ls`/`cat`…）**都在 `/usr/bin`** ✅。
`update.py` 用 `sys.executable` ✅，`main.py` 用 `git` ✅，
`cl-bg.py` 已经 `os.chdir(HERE)` 所以 cwd=`/` 不是问题 ✅。

→ **补两条绝对路径就行，不用改 PATH 环境。**

### 5.3 双击失败是**静默**的

ClassLive 是 `.accessory`（无 Dock 图标），日志在 `~/Library/Logs/ClassLive/bg.log`，
但用户不会去翻。**启动失败得弹个东西出来。**
