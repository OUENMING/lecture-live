# 云端定稿模型调研（2026-10-10）

> 问题：漏句丢在本地 Whisper 定稿（turbo int8 greedy）。换云端能不能更准、更快、更省？选谁？
> 结论一句话：**草稿留本地 Parakeet；定稿走 Groq → Cloudflare → 千问 3.1 兜底链；本地 Whisper 降为可选。**
> 三人一学期预计 **$0–1**，最坏 **≈$5**。

## 1. 量具

- **真值**：MIT OCW 14.01 F18 Lec 11（Monopoly I），50.5 分钟，人工字幕 8,306 词（`archive.org/download/MIT14.01F18/MIT14_01F18_lec11_300k.{mp4,srt}`）。
- **切段与生产一致**：离线复刻 `capture.PeakNormalizer` → `vad.Segmenter`（同一份代码），得 **322 段**（≤12 s，有声合计 2,971 s）。各家喂的是同一批段。
- **判据**：WER（difflib 对齐，`scripts/stream_metrics.normalize` 归一化，数字转词）；
  **漏段** = 参考里连续 ≥5 词、假设只出 ≤30% 的片段（ClassLive 关心的「整句没了」）。
- 延迟：都柏林家宽，逐段请求的端到端墙钟（含上传）。
- 脚本与各家原始输出：`docs/experiments/cloud_asr_20261010/`（见 §7）。

⚠️ **n=1 节课，单讲者、讲台麦**。比 Owen 的教室远场录音干净；0.5 个百分点 ≈ 40 个词，不算可靠差距。

**读法**
- 云端 Whisper 比本地准，主因疑似本地 **int8 + greedy**（CF 是 beam 5）；漏段 2.5% → 0.7%，这正是要解决的问题。

- Mistral 漏段 2.0% 接近本地 Whisper → **排除**（且账号「允许训练」开关是开的）。
- nova-3（CF 上的 Deepgram）切片 12.1%，比 turbo 差且贵 10 倍 → 排除。
- 加「前一句当提示」（CF）：8.4% → 8.2%，基本无用。

## 3. 架构结论

| 层 | 选择 | 理由 |
|---|---|---|
| 草稿（每秒重转） | **本地 Parakeet**（后续可换 Nemotron 流式，见 `PLAN-streaming-asr.md`） | 每秒一次请求不适合按段/按次计费；流式云 $0.36–0.55/h；本地免费 0.35 s |
| 定稿（每段一次，~322 次/节） | **云端兜底链** | 更准、漏得少，Groq 还比本地快 6 倍，省 CPU/电 |
| 离线兜底 | **本地 Parakeet** | OCW 上 Parakeet 漏段 2.6% ≈ Whisper 2.5%，只是错字多；断网那节课不会更漏句 |
| 本地 Whisper | **降为可选「离线增强」** | 新用户少下 ~1 GB，上课少占 CPU/内存 |
| 课后精修 | 千问 3.1 filetrans 整文件重跑 | 8.2% / 漏 0.4%，$0.013/节 |

**兜底链**：Groq（免费、最快）→ Cloudflare（每天约 4 节免费）→ 千问 3.1 flash（最准、便宜）→ 本地 Parakeet（断网）。
超时 / 429 / 5xx 就降一级；千问对纯静音段返回 400 `ASR_RESPONSE_HAVE_NO_WORDS`，**当空文本、别重试**。

## 6. 外部方案评估：「远场英文课堂黄金流水线」（2026-10-10，来源为聊天里贴来的 AI 回答）

原方案四步：①DeepFilterNet/RNNoise 降噪去混响 → ②Silero VAD → ③Cohere Transcribe 2B 或 Parakeet-TDT 1.1B → ④WhisperX 强制对齐 + LLM 笔记。

| 步骤 | 判定 | 依据 |
|---|---|---|
| ① 降噪/去混响「Crucial」 | ❌ **本项目已实测否决** | `experiments/denoise_ab.py`：GTCRN 词数 −41%、DPDFNet −18%，置信度和术语命中都变差（含 5 种顺序对照排除电平混淆）；`dereverb_ab.py`：WPE 测不出效果、空转写翻倍。外部文献同向：arXiv 2512.17562 在 40/40 个配置里降噪后 WER 都更差（Whisper 10 dB 下 8.8%→25.8%）；Iwamoto 2022 指出单通道增强的伪影是主因 |
| ② Silero VAD | ✅ **已经在用** | `vad.Segmenter` |
| ③a Parakeet-TDT 1.1B | ❌ | 纯英文旧模型；同家族 0.6B v3 在本课实测 **14.3% / 漏 2.6%，是 8 个系统里最差**——「非自回归对远场更强」与本项目数据相反 |
| ③b Cohere Transcribe 2B | ⚠️ **值得测，但理由要改** | 真实存在（2026-03-26 发布，Apache 2.0），Open ASR 榜曾第一（5.42%，Interspeech 2026 论文口径 5.84%）。但它是 **Conformer 编码器 + Transformer 解码器 = 自回归解码**，原方案说它「非自回归」是错的。榜单是干净朗读为主，**本课实测才算数**（各厂标称 5–6%，CF-turbo 实测 10.5%） |
| ④ WhisperX 强制对齐 | ➖ 不需要 | 千问 / Groq（verbose_json）都已返回时间戳；ClassLive 按段已有时间 |
| 「复读机幻觉是主要风险」 | ➖ 不是本项目的主要问题 | 实测本项目的问题是**漏**（删除率 3.5–5.1%）不是复读；已有 `is_degenerate` 兜底 |
| vLLM 部署 | ❌ 形态不符 | 那是 GPU 服务器批处理；ClassLive 是每台 Mac 实时、零服务器（VPS 2 核 1.9 GB 放不下） |

**能拿走的只有一条：Cohere Transcribe 进候选** —— ✅ **已实测（2026-10-10 晚）**：逐段 WER **10.0%**、漏段 0.7%、p50 0.64 s（服务器 Google 堪萨斯城）。与千问 9.9% / Groq 10.4% **在噪声内打平**，榜单上的领先在讲课录音上没兑现。trial key 响应头 `x-endpoint-monthly-call-limit: 1000`、实测限速约 5 次/分（322 段跑了 75 分钟）→ 一个月只够约 3 节，且条款禁生产 → **不进兜底链**。 两条路：
- **API**：Cohere trial key 免费但限速，条款写明**不得用于生产/商业**；生产要包专属 Model Vault → 不适合当在线定稿，**只适合拿来测准确度**。
- **本地**：社区 GGUF（handy-computer，Q4_K_M 1.56 GB，LibriSpeech-clean 1.24%）。可作「离线增强」替代本地 Whisper 的候选，但 2B 在 Mac CPU 上能否跟上实时**未测**。

## 8. 第二份外部方案评估：「低信噪比保守处理链」（2026-10-10 晚）

原链：80 Hz 高通 → DeepFilterNet3 限衰减 −12 dB（或 70/30 干湿混合）→ EBU R128 −23 LUFS → VAD → Parakeet-TDT 1.1B；另提目标说话人提取（SpEx+/VoiceFilter）与 2–4.5 kHz 提亮。

| 项 | 判定 | 依据 |
|---|---|---|
| 诊断：瓶颈是信噪比，放大音量改变不了 | ✅ 与本项目一致 | 10-09 实测人声块与停顿块只差 2.1 dB（`PLAN-audio-gain.md`） |
| 降噪会吞辅音、导致删词 | ✅ 与本项目一致 | `denoise_ab.py` 逐段可见整句被删 |
| 保守降噪 / 干湿混合 | ❌ **已测过** | `denoise_ab.py` 的 Observation Adding（降噪与原始按比例混合）α=0.3/0.5/1.0：词数 466/469/422，**仍低于原始 541** |
| DeepFilterNet3 能在 0 dB 下剥离人声 | ⚠️ 未测这个型号 | 测过同类 DPDFNet（−18% 词数）、GTCRN（−41%）；文献 40/40 配置变差 |
| −23 LUFS 响度归一 | ➖ 已有等价物 | `capture.PeakNormalizer`；Parakeet 对绝对电平敏感（实测等比衰减后词数 73→6），换归一化口径有风险 |
| 80 Hz 高通 | ➖ 便宜但预期收益≈0 | 识别模型的 mel 特征本来就几乎不用 80 Hz 以下；未测，可顺手 A/B |
| 2–4.5 kHz 提亮 | ➖ 预期≈0 | 静态 EQ 在 log-mel 上是逐频带常数偏移，Parakeet 的逐特征归一会抵消大半；未测 |
| 目标说话人提取 | ❌ 不做 | 研究模型、要录讲师声纹、错判即整句删除（正是我们要消灭的漏句） |
| Parakeet-TDT 1.1B | ❌ | 同家族 0.6B 本课最差 |

**结论**：诊断对，药方本项目大多已试过且失败。真正改变信噪比的是**物理距离**（坐前排 / 外接麦放讲台），以及换更抗噪的识别器（上云后漏段 2.5% → 0.7%）。
若要再试前端，只剩「80 Hz 高通」值得一个零成本 A/B；但**缺远场真值**——要先有一段 Owen 教室录音的人工转写（5 分钟即可）才谈得上量。

## 9. 用户零操作 + 无缝切换 + 草稿层（2026-10-10 深夜，设计评估，未动代码）

### 9.1 零配置：所有 key 留在 Owen 的 Cloudflare Worker 里
```
用户 Mac ──(公开的 install token，同 ingest 那套)──▶ Owen 的 Worker（CF 都柏林边缘）
                                                   ├─ Groq            （Worker secret）
                                                   ├─ Workers AI turbo（**binding，连 token 都不用**）
                                                   ├─ 千问 3.1 flash  （Worker secret）
                                                   └─ DeepInfra turbo （Worker secret，预充值）
用户 Mac 本地 Nemotron/Parakeet ◀── Worker 回 503 或断网时
```
- 用户侧**零操作**：不注册、不填 key；客户端只认一个 URL。key 不进安装包（发出去就等于公开）。
- 现成基础：上传已经走 `ingest.bldcam.page` 这个 Worker + 公开 write-only token，同一套鉴权思路。
- 多一跳的代价：Worker 在 CF 都柏林边缘，Groq/CF 本身也在 CF 后面 → 预计 +10–30 ms（**未测**）。
- Workers 免费档（**实现前回源核**）：10 万请求/天（一节课 322 次 → 约 300 节/天）、每请求 10 ms CPU（等上游的时间不算）。
- ⚠️ **产品承诺要改**：README 写「音频不出本机」。上云定稿 = 音频片段经 Owen 的 Worker 发给第三方。
  需要：①首次使用明确告知 + 可关（关了退回纯本地）②只选**不留存/不训练**的供应商（Mistral 账号训练开关是开的，本来也排除了；Groq/千问/DeepInfra 的留存条款**实现前逐家核**）。

### 9.2 无缝切换：可行，而且天然适合
每段是**独立请求**，切换不需要「迁移会话」——下一段换家发就行，用户看到的只是同一条字幕。

| 机制 | 做法 |
|---|---|
| 被动 | 429 / 5xx / 超时 → 同一段**立即**改发下一家；Groq 的 429 带 `retry-after`，记下「冷却到几点」，期间直接跳过 |
| 主动 | Groq 每个响应都带 `x-ratelimit-remaining-requests`（= 当日剩余 RPD）→ 剩 <5% 就提前降级，不等撞墙 |
| 抢跑（可选） | 主路 1.5 s 没回 → 并发打第二家，先到先用（偶尔双份计费，换 p95） |
| 预算闸 | Worker 记当月付费估算，超上限 → 回 503 → 客户端退本地，不会意外烧钱 |
| 状态存哪 | 冷却时间与日计数放 KV（最终一致，够用）；要精确再上 Durable Object |

顺序（按「免费→便宜→最准」）：**Groq → Workers AI turbo → 千问 3.1 flash（前 13 节免费）→ DeepInfra turbo（$0.010/节）→ 本地**。
副作用：不同家标点/数字写法略有差异（"10%" vs "ten percent"），对翻译无影响；同一节课内会混。

### 10.3 「要等一大段才翻译、然后一下子全出来」—— 根因已定位（10-09 真课 `.live.jsonl` 现算）
**现象量化**：教授在讲话（期间 ≥4 条英文草稿）却 ≥6 s 没有新中文：**57 次，共 437 s（占全课 15%）**；≥10 s 的 4 次。

**根因 ①（主因）：草稿译文的触发条件会「饿死」。** `draft_policy.should_translate` 要求「比上次送翻译时**多 ≥6 个词**」。
但 Parakeet 每秒重转、词数会忽多忽少，而且只转最近 10 s（`PARTIAL_MAX_S`）→ 词数有天花板。
一旦在词数高点送过一次，本段剩下的时间就再也凑不够「+6」。
实例（seg 91，888–901 s）：891.2 s 送翻译时 19 词 → 之后 13/17/19/22/20/23 词，门槛 25 永远到不了 → **10 s 没有新中文**，直到段尾定稿 4.4 s 后两句一起出来。
`clause` 档的「饿死兜底」（≥6 s 照送）也救不了，因为 `+6 词` 的前置检查在它前面就 `return False` 了。

**根因 ②：草稿翻译和定稿共用一条线程，定稿优先。** 定稿在排队时，草稿识别直接跳过（`partial_worker`），草稿译文也排在后面（`final_worker`）。
回放模拟里 legacy 规则应触发 570 次，真课实际只出了 417 条 → **约 27% 被挤掉**。

**根因 ③：定稿要等段尾 + 处理。** 段最长 12 s，段尾到定稿 p50 3.8 s（本地 Whisper 2.7 s + 翻译），一段里的几句同时出 → 「一下子全部出来」。

**离线回放验证（同一节课，翻译耗时按 1 s 计，未计线程挤占）**：
| 触发规则 | 草稿译文条数 | 讲话中 ≥6 s 无新中文 | 其中 ≥10 s |
|---|---|---|---|
| 现行 legacy（回放） | 570 | 52 次 / 398 s | 3 |
| **改：比上次送出的文本多 ≥4 个新词，或距上次 ≥5 s 且有新词** | 809（+42%） | **3 次 / 23 s** | **0** |

修法（按收益/代价排序）：
1. 改触发判据（`draft_policy.py` 一处，+42% 草稿翻译请求，DeepSeek 费用很小）——**最大头**。
2. 草稿译文单独一条线程，不再被定稿挤掉。
3. 定稿上云：段尾→定稿少 1–2 s（取决于实测延迟）。
4. 草稿换 Nemotron 流式：文本只追加不回改，「新词数」判据天然可靠。
**不建议**缩短 12 s 硬切：会多出半句切断，定稿准确度下降。
⚠️ 以上在 Owen 自己的课上量的（云端翻译）；反馈用户若用本地翻译，草稿译文更慢，空窗会更长——**要问清他用的是哪档**。
⚠️ 改触发后草稿中文会更频繁地被改写（闪），上线前要用真课回放看一眼。

## 11. 「翻译空窗」的业内做法 + DeepInfra 慢在哪（2026-10-11）

### 11.1 同类产品 / 研究怎么做（一手来源）
| 谁 | 做法 | 来源 |
|---|---|---|
| **LecSync 1.0.60**（本机，asar 解包读源码） | 显示单位是**句子**：草稿里一出现完整句就单独翻（`translation.sentence`）；没说完的尾巴也翻（`tailTranslation`），**半透明显示**；分段档位 快速=一句一段 / 平衡=约三句一段（默认）/ 完整=约八句；另有「句子显示模式」按标点、换人、停顿分组。翻译在服务端做（后端疑似 Soniox，**推断**） | `dist/renderer/assets/index-*.js`、`styles-*.js` 的中文文案 |
| **Soniox** | 识别与翻译是**同一个流**，译文 token **句中逐词流出**，不等句尾 | soniox.com/docs 实时翻译页 |
| **LiveCaptions-Translator** | 遇句末标点**立刻**送翻；没句末时，原文**变化 3 次**（`MaxSyncInterval=3`）或 **1.25 s 不变**（`MaxIdleInterval=50`×25 ms）就把半句也送去翻 —— 数的是「变化次数」，不是「词数差」 | `src/Translator.cs:130-153`、`Setting.cs:18-19` |
| **Google 翻译实时模式** | 每来新词**整句重译**；用 mask-k（藏住最后 k 个不稳的词）+ 偏向上一版的 beam 抑制闪动 | Arivazhagan 等 ICASSP 2020；Google Research 博客 |
| **whisper_streaming / SimulStreaming（ÚFAL，IWSLT 2025 第一）** | LocalAgreement：**连续两次假设相同的前缀**就确认；LLM 翻译端输出分 `text`（已确认，只增不改）与 `unconfirmed_text`（可改，可先给用户看） | GitHub 两个仓库 README |

共同点：**不等「一段」结束**——要么按句子、要么按稳定前缀、要么定时把半句送去翻；未确认部分用视觉区分（灰/半透明）而不是不显示。

### 11.2 对 ClassLive 的启发（按代价排序）
1. **修触发判据**（§10.3）：改成「比上次送出的文本多 ≥4 新词，或 ≥5 s 有新词」（与 LiveCaptions-Translator 的「变化次数 / 空闲时间」同思路）。回放：讲话中 ≥6 s 无新中文 398 s → 23 s。
2. **草稿译文单独线程**：不再被定稿挤掉（现在约 27% 被挤）。
3. **句子级提前定稿（LecSync / LocalAgreement 思路）**：草稿里一个完整句连续两次不变 → 当场按「定稿」翻译上屏；段尾真定稿到了只在**明显不同**时替换。
   已有数据（10-09，Parakeet 草稿）：覆盖 17.2% 的定稿词、比定稿**早 p50 10.7 s**，但与定稿逐字不一致 29.6%（含两个模型正常措辞差，是上界）。
   **换 Nemotron 流式后**（回改率 0.5%）这条会可靠得多 —— 两件事应该一起做。
4. 显示：已确认中文实色、未确认尾巴灰色（LecSync / SimulStreaming 同款），而不是等它稳定才显示。
5. 不建议：缩短 12 s 硬切（伤定稿准确度）；Soniox 式端到端（要整体换云端流式服务，$0.12/h 起，且音频全上传）。

### 11.3 DeepInfra 为什么慢（实测拆账）
用原生接口 `/v1/inference/<model>`，它会回 `inference_status.runtime_ms`（服务端真正算的时间）：
| 模型 | 墙钟 p50 | 服务端计算 p50 | 差值（排队 + 网络） |
|---|---|---|---|
| Qwen3-ASR-1.7B | 5.38 s | **0.49 s** | **≈4.9 s** |
| whisper-large-v3-turbo | 1.69 s | 0.77 s | ≈0.75 s |
→ **不是模型慢，是排队**：Qwen3-ASR 是冷门模型，看起来副本很少，请求在 DeepInfra 那边排队。网络部分（犹他）≈0.5–0.8 s。
试过的办法：
- `service_tier=priority`（官方说能插队，1.5×价）：响应里**没回显**，p50 5.32 s vs 5.05 s → **语音模型不支持**。
- `fail_fast=true`（官方说没空位立刻回 429）：12 次全 200、最慢 16 s → **语音模型不生效**。
- **上传改 Opus 24k**：384 KB → 36 KB，p50 5.05 → 3.46 s → **有用，生产应该这么传**（任何供应商都适用）。
- 论坛：没找到 DeepInfra 语音延迟的专门讨论；OpenAI 社区里 Whisper API 慢的帖子结论都是「切小段 / 自建」。
剩下的解法：专属部署（租 GPU 按小时计费，3 个人不划算）；或客户端设超时（如 2.5 s）后改发下一家。
**结论不变：DeepInfra 只当兜底，主路用 Groq。**

### 13.5 草稿送翻：功能词结尾
`novel` 触发下 13% 的草稿以 of/to/the/is… 结尾送去翻（半截短语）。回放两种处理：
- 送前**剥掉结尾的悬挂词**（复用 `main.DANGLING_TAILS`）：零延迟；
- 结尾是功能词就**最多再等一份草稿**（约 1 s）：半截比例 13% → 7%，空窗不变差（2 次 15 s → 1 次 6 s）。
→ R1 用前者（零延迟），后者备选。

### 13.6 外部 AI 指出的 `carry` 问题 —— 属实
`main.final_worker` 用**整段**文本判断「没说完」：`is_incomplete(text) and len(text.split()) < 25`。
- 12 s 硬切的段一般 >25 词 → 长度条件直接挡掉 carry，末尾半句单独翻译上屏；
- `is_incomplete` 只认「最后一个词在 `DANGLING_TAILS` 里」，无句末标点但以实词结尾的半句也放过；
- 段 <25 词时又会把**已说完的前一句**连同半句一起扣住，最多晚 5 s（`CARRY_MAX_S`）。
10-09 真课：285 对相邻段里，前段末句无句末标点 **91 次（32%）**，其中 48 次是被「≥25 词」挡掉的；后段**小写开头（明显被劈开）43 次**。
修法：先 `split_sentences`，前面完整的句子立刻上屏，**只把最后一句**拿去判断要不要 carry。

## 14. 离线实验：12 s 硬切时往回找能量低谷再切（2026-10-11）
做法：同一节 OCW、同一套生产切段；对 157 个 12 s 硬切点，在切点前 1.5 s 内按 30 ms 帧算能量（3 帧平滑），挪到最低点切，切掉的那截并进下一段（中位往回挪 0.71 s，下一段最长 13.2 s）。同一 Groq + Opus 24k 逐段跑。
| | WER | 删除率 | 漏段 | 前段末尾无句末标点 | 后段小写开头（被劈开的代理指标） |
|---|---|---|---|---|---|
| 原切点 | 10.1% | 4.0% | 0.4% | 95 | 118 |
| **往回找低谷** | **9.9%** | **3.6%** | 0.4% | **83（−13%）** | **95（−19%）** |
→ WER 差在噪声内，但「把一句话劈成两半」的迹象少了 13–19%，删除率也略降。改动小（`vad.Segmenter` 硬切分支约 25 行）。
⚠️ 「小写开头」只是代理指标（Whisper 的大小写本身不稳）；生产里下一段会从挪回的位置接着累积，与离线「并进下一段」等价。
**生产实现复核（2026-10-11，`vad.find_valley_cut` 进 `Segmenter` 后重切 OCW + Groq Opus）**：333 段（原 322，挪回的尾巴让下一段更早满 12 s，硬切 157 → 167），回退中位 0.795 s；WER 10.4%（原 10.1%）、漏段 0.8%（原 0.4%，多出的都是口头禅类短片段，见 eval 输出）→ **准确度在噪声内无变化**；「后段小写开头」118 → **86（−27%）**、「前段无句末标点」95 → 85。结论：不提升识别准确度，只减少劈句；默认开、`CLASSLIVE_VAD_VALLEY=0` 可关。
