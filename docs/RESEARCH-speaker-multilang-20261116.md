## 1. 结论

不是二选一，也不改 11-14 定的顺序（U → S 穿刺 + P0 → P1 → P2 / P3 → P4 / P5）。两个功能插在两处：

1. **现在**（与 U 线并行，不碰上课路径）：半天穿刺，量 Soniox 实时分离在远场单麦上准不准（§5）。
2. **P0-1 录回放磁带时**：多录一盘「开分离 + 中英语种提示」的讨论磁带。回放判据是后面每一刀的安全网，磁带里没有这两个字段，以后加功能就没有判据。
3. **P1 契约**：`Tok` / `Sealed` / `("final", …)` 事件 / `Row` 加 `speaker`、`lang`（默认空）。契约写明「可增」，以后加也行；放在 P1 做的好处是 `("final", …)` 现在是位置元组加 `len` 守卫（`main.py:4389`），P1-1 正好把它换成 dataclass。
4. **P1 之后**：桌面版「讨论模式」D1 + 中英混说 L1（合计约 1 周）。
5. 网页版 P4 / P5 照旧；Soniox 官方 Web SDK 里分离、语种都是配置项，网页版拿到的核心已带这两个字段。

想更早用上（不等 P1）：只有「课后异步重跑」这条路不碰实时链路（D3 单做，2–3 天），实时显示要等 P1。

## 7. 原生 Windows 版 vs 网页版（11-16 Owen 追问）

网页版更简单，而且它本身就能在 Windows 上用。11-14 已定「原生 Windows 先放」，本节是把理由摆出来，不是改决定。

| | 网页版 | 原生 Windows 版 |
|---|---|---|
| 界面 | 新写一套 Svelte（第一版只有字幕 + 小窗 + 笔记页） | 重写 AppKit 界面：直接 import AppKit / objc 的模块 21 个约 28,000 行（11-14 量），悬浮窗一项就 5,705 行 |
| 抓声音 | 浏览器 API；Windows 的 Chrome / Edge 能抓整机声音（底稿 A5） | python-sounddevice 官方包不支持 WASAPI loopback（截至 2025-10），要换库 |
| 本地模型 | 不做（已定） | mlx 只有 Apple 芯片能跑，要换后端；Windows 上 sherpa-onnx 的可用性没测 |
| 安装与更新 | 没有：打开网址就是最新版 | 现在是 `.app` + `git pull`，Windows 要另做安装包、签名、更新 |
| 测试机 | 任何有 Chrome 的机器 | 要一台 Windows 机器长期跑真课 |
| 前置重构 | P0–P2（5–7 周） | 同样要 P0–P2，否则是把 3,116 行的 `run()` 再抄一份 |
| 重构之后的工期 | P4 + P5：4–6 周（11-14 估计） | 没有估过。Claude 的粗估 6–10 周，低置信，没有任何实测 |
| 做完之后要养的 | 一份核心 + 两套界面 | 一份核心 + 三套界面（若网页版也做） |

以后真想要 Windows 桌面形态：把网页版用 Tauri 包一层（底稿里已核 Tauri v2 的 sidecar），比从 AppKit 移植省得多。

## 8. 公开语料穿刺结果（11-16 实跑，每组只跑 1 次）

脚本、音频、原始消息都在仓库外：`~/.classlive/eval/diar_spike/`（`code/run.py` 按实时速度推流，`score.py` / `score_cs.py` 评分）。模型 `stt-rt-v6`，欧洲区，test key。

### 8.1 说话人分离：AMI IS1009a（4 人英文会议，14 分钟，单个远场阵列麦 Array1-01，人工 RTTM）

量法：每个 final token 的中点落在哪位参考说话人的发言段（±0.25 s），Soniox 标签按最优一对一映射。**不是标准 DER。**

| | 端点检测开（现行） | 端点检测关 |
|---|---|---|
| 认出的人数（参考 4 人） | 4 | 3（漏掉说话最少的一位，68 s） |
| 单人说话段，按词标错 | 8.0%（2445 词） | 6.2%（2380 词） |
| 重叠说话段，标到其中一人 | 86.4% | 94.5% |
| 按句标错（句内多数词错才算错） | 18.4%（353 句） | 7.4%（257 句） |
| final 延迟 p50 / p90 | 2.04 / 5.87 s | 5.87 / 6.72 s |
| non-final 首次标签与最终不同 | 0.5% | 0.4% |

读法：英文、4 人、远场下，按词错 6–8%，低于 §5 的 20% 建议闸门。non-final 上的标签基本就是最终标签，封口时就能用。关端点检测换来的准确率有限，代价是 final 晚约 4 秒、还漏了一个人 —— **不值得关**。按句错 18.4% 偏高，两组句数差很多（353 对 257），成因没查。

### 8.2 中英混说：ASCEND test 第 2 场（两人对话，近讲麦，283 句拼成 12 分钟，人工转写）

量法：混合错误率（中文按字、英文按词），参考与识别都去标点；数字写法（four / 4）没归一，英文句的数字偏高一点。

| | `language_hints: ["en"]`（现行） | `["en","zh"]` |
|---|---|---|
| 合计错误率 | 27.1% | 11.8% |
| 纯中文句（130） | 27.4% | 9.2% |
| 纯英文句（91） | 42.9% | 18.5% |
| 混说句（62） | 19.0% | 11.1% |
| 语种标签正确 | 87.3% | 98.7% |
| final token 数 | 3888 | 2879 |

读法：只给英文提示时中文**照样出汉字**（130/130 句），不是乱码；差在多出约 300 个「嗯」「对」和把 cool 写成「酷」。加上中文提示后错误率降一半多。

**这份语料量不了说话人分离**：数据集里的句子不是按对话顺序排的（一个人的全部句子在前、另一个人在后），拼出来不是真对话。顺带的观察：Soniox 把两个人几乎全标成了同一个人，原因没查，不作数。

### 8.3 还没覆盖的

远场 + 中英混说 + 多人，三样同时出现的公开语料没找到；真实小组讨论录音仍然要量一次。每组只跑了 1 次，没有重复。

### 8.4 纯英 / 纯中：语种提示有没有用（11-16，每组 1 次）

Owen 11-16 说明：目前场景没有中英混说，要么纯英要么纯中。于是量这两种。量法：整段错误率（英文按词、中文按字，去标点），都开 `enable_language_identification`、端点检测开、不开分离。

| 语种提示 | 纯英文课（MIT 14.01 第 11 讲前 10 分钟，人工字幕 1520 词） | 纯中文（ASCEND 第 1 场纯中文 216 句，7 分钟，1383 字） |
|---|---|---|
| `["en"]`（现行） | 8.7% | 8.6% |
| `["en","zh"]` | 8.6% | 8.5% |
| 不给提示 | 8.7% | 8.7% |
| `["zh"]` | — | 8.5% |

语种标签：英文课 2739 个 token 全标 en；中文段标错 0.5–0.7%（不给提示时 10/1885）。

11-17 复核生产配置（`build_context(课名, 8 个术语)`，即带 `("language","English")`）：

| | 错误率 | 语种标签错 | 判出语种（累计 20 个 token 且 ≥90% 同语种） |
|---|---|---|---|
| 英文课，关语种识别（现行） | 8.9% | —（不给标签） | — |
| 英文课，开语种识别 + 生产 context | 8.9% | 0.0% | 24 s（课从 12 s 才开讲） |
| 中文段，开语种识别 + 生产 context | 8.5% | 0.8% | 12.5 s（无 context 时 7 s） |

开语种识别对英文课零代价；英文 context 不会把中文识别带歪。

读法：单一语种时提示给什么都一样，Soniox 自己认得出。**不用改 Soniox 的提示**；要「自动」的是 ClassLive 这一侧：打开语种识别，按第一句封口句的语种决定走「英 → 中翻译」还是「中文只转写」。8.2 的差距只出现在混说里。
